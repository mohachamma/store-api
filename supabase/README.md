# Database (Supabase / Postgres)

Nothing here needs a Supabase project to be written or tested: `npm test` runs every migration and the seed on an
in-process Postgres (PGlite) and checks constraints, RLS and the order privacy rules.

## Files
| File | Purpose |
|---|---|
| `migrations/20261124000001_core_schema.sql` | Tables, constraints, RLS policies, order functions, admin event trigger |
| `migrations/20261124000002_geo_data.sql` | 58 wilayas + 1541 communes (generated by `scripts/gen-geo.mjs`). **Shipping fees are placeholders.** |
| `migrations/20261125000004_brands_offers.sql` | Brands can be hidden / linked; `offers` banners with schedule and countdown; public settings `brands_strip` and `sale_page` |
| `seed.sql` | 16 sample products, looks, a collection, a promo code (generated by `scripts/gen-seed.mjs`). Development only. |

## Applying it later (when the Supabase project exists)
Do this only when the owner creates the project (not yet). Either:
- Supabase CLI: `supabase link --project-ref <ref>` then `supabase db push`, and `supabase db reset` locally for the seed; or
- Paste the migration files, in order, into the Supabase SQL editor. Run `seed.sql` only on a development project.

## Model in short
- **Catalog:** `categories`, `brands`, `products` → `product_images`, `product_variants` (size, color, stock, price, compare-at price); `collections` ↔ `products`; `looks` ↔ `products`; `slides`; `site_settings`; `discount_codes`.
- **Geography:** `wilayas` (home/desk fee per wilaya), `communes`.
- **Customers:** `customers` (profile for an `auth.users` row), `favorites`.
- **Orders:** `orders` + `order_items` (name/size/price snapshots), `admin_events` (live feed for the dashboard, no personal data).
- Translatable text is jsonb: `{"ar": "...", "fr": "...", "en": "..."}`; `ar` is mandatory.
- Money is integer DZD. Totals must satisfy `total = subtotal + shipping_fee - discount_total` (CHECK).

## Privacy rule (enforced by the database)
Customer name, phone, commune and address can exist **only while an order is `pending`** (CHECK `orders_pii_pending`).
`confirm_order()` stores the delivery company's tracking number and erases them in the same statement; `cancel_order()` erases them and restores stock;
`expire_pending_orders(days)` (for the Vercel Cron cleanup) cancels stale pending orders. These functions are executable by the service role only.

## Access model
- The API uses the **service role** (bypasses RLS). RLS still protects every table against the anon/authenticated keys:
  public can read published catalog data only; customers see their own profile, favorites and orders; admins (`app_metadata.role = 'admin'`) can do everything.
- `discount_codes`, `orders`, `order_items`, `admin_events` are never readable by anonymous visitors.
