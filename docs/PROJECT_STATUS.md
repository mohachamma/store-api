## 1. نظرة عامة

متجر إلكتروني للملابس للسوق الجزائري، مقسوم إلى ثلاثة مستودعات مستقلة بلغة TypeScript:

| المستودع | الدور | الرابط |
|---|---|---|
| `store-api` | الخادم: قاعدة البيانات، قواعد العمل، الدفع، شركة التوصيل | https://github.com/mohachamma/store-api |
| `store-web` | واجهة الزبائن (Next.js) — عربي/فرنسي/إنجليزي | https://github.com/mohachamma/store-web |
| `store-admin` | لوحة التحكم للمدير والفريق (Next.js) — عربي/فرنسي | https://github.com/mohachamma/store-admin |

**القاعدة الذهبية (قاعدة المالك):** كل ما يظهر في المتجر يجب أن يكون قابلاً للتعديل من اللوحة. أي إضافة جديدة في الواجهة تحتاج ثلاثة أشياء: حقل في قاعدة البيانات والـ API، وعرضه في المتجر من الـ API، وصفحة تعديل في اللوحة.

**طريقة العمل:** أعدّل على فرع جانبي، ثم أفتح Pull Request فيه ملخص، ثم أدمج في `main` بعد موافقة المالك. كل دمج في `main` ينشره Vercel تلقائياً (للمتجر واللوحة). لا نستخدم GitHub Actions.

## 3. سجل العمل (الأحدث أولاً)

### 2026-11-26 — المرحلة 4: الطلبات والدفع عند الاستلام (الثلاثة معاً)
**ما عملته:**
- **الـ API (الأهم، وهو المسؤول عن الأمان):**
  - الزبون يرسل فقط رقم القطعة والكمية، والخادم هو من يحسب **الأسعار والتوصيل والخصم والمجموع** من قاعدة البيانات. لا يمكن للمتصفح أن يتلاعب بالسعر.
  - **المخزون:** يُحجز مع الطلب في عملية واحدة؛ إن فشل أي سطر يُلغى كل شيء. وإن طلب زبونان آخر قطعة في اللحظة نفسها ينجح واحد فقط (جرّبته).
  - **التوصيل:** سعر الولاية للمنزل أو المكتب، ومجاني إن تجاوز الطلب 10 000 دج (قابل للتعديل لاحقاً من اللوحة).
  - **كود الخصم:** نسبة أو مبلغ ثابت، بحد أدنى للطلب وتاريخ انتهاء وعدد استعمالات، ويُحتسب مرة واحدة.
  - **حماية من الإزعاج:** حتى 3 طلبات معلّقة في الساعة لكل رقم هاتف. ويُوحَّد شكل رقم الهاتف الجزائري.
  - صفحة الزبون لطلبه تحتاج رمزاً سرياً ولا تعرض أبداً اسمه ولا هاتفه ولا عنوانه.
  - **للمدير:** قائمة الطلبات بالفلاتر، التفاصيل، **تأكيد الطلب** (يحفظ رقم التتبع ويمسح بيانات الزبون الشخصية في العملية نفسها)، تسلسل الحالات (شُحن ← سُلّم أو أُرجع)، **الإلغاء يعيد المخزون**، والدفع عند الاستلام يصبح "مدفوعاً" عند التسليم.
  - **الإحصائيات:** مداخيل اليوم والأسبوع والشهر (لا تُحتسب الطلبات الملغاة أو المرجعة)، الأكثر مبيعاً، تنبيه المخزون، بتوقيت الجزائر. و**إشعارات الطلب الجديد**.
- **المتجر:** صفحة إتمام الطلب (الاسم، الهاتف، الولاية والبلدية، العنوان، نوع التوصيل، كود الخصم، ملخص بأسعار الخادم)، وصفحة تأكيد الطلب. جرّبتها في متصفح هاتف: طلب بـ 2 400 + 500 توصيل = 2 900 دج.
- **اللوحة:** شاشة الطلبات (تبويبات حسب الحالة، بحث، تفاصيل، اتصال وواتساب مع الزبون، تأكيد، تغيير الحالة، إلغاء، طباعة بطاقة التوصيل)، و**جرس الطلب الجديد** (شارة تتحدث كل 20 ثانية مع صوت تنبيه)، وصفحة "نظرة عامة" بإحصائيات حقيقية.
**الخصوصية:** بعد تأكيد الطلب لا يبقى في قاعدتنا اسم ولا هاتف ولا عنوان، وتختفي من شاشة المدير أيضاً.
**ما يهمّك:**
- التأكيد حالياً يدوي: تدخل رقم التتبع الذي تحصل عليه من شركة التوصيل. المرحلة 6 تجعله تلقائياً مع الشركة التي تختارها.
- الدفع بالبطاقة (CIB/الذهبية) يظهر في المتجر "قريباً" إلى أن نضيف Chargily.
- حسابات الزبائن والمفضلة (من المرحلة 4 الأصلية) لم أبدأها بعد: تحتاج Supabase.

### 2026-11-26 — ربط المتجر واللوحة بالـ API (اختُبر والثلاثة تعمل معاً)
**ما عملته:**
- **الأنواع من الـ API نفسه:** المتجر واللوحة صارا يولّدان أنواعهما من `/openapi.json` بدل الأنواع المكتوبة يدوياً، فلا يمكن أن تختلف الأجزاء الثلاثة دون أن يكتشف المترجم ذلك. هذا كشف خللاً حقيقياً في الـ API: الصورة الرئيسية (التي قد تكون فارغة) كانت موثّقة على أنها دائماً موجودة؛ أصلحته وأضفت اختباراً يمنع عودته.
- **المتجر:** يقرأ كل شيء من الـ API الحقيقي (الرئيسية، التشكيلة، المنتج، البحث، التخفيضات، الإعلان). لا يتعطل إن غابت الصورة الرئيسية، ويقبل روابط خارجية من اللوحة. وبناؤه لا يفشل إن كان الـ API غير متاح لحظة البناء.
- **اللوحة:** كل شاشاتها (العلامات، العروض، نص الإعلان) تعمل على الـ API الحقيقي. وأضفت شاشة **عنوان صفحة التخفيضات** (كانت ناقصة). صفحة "نظرة عامة" تعرض رسالة واضحة بدل الانهيار لأن مسار الإحصائيات سيُبنى مع الطلبات.
- **بيئة محلية كاملة بأمر واحد** `npm run dev:local` في `store-api`: قاعدة بيانات في الذاكرة بالبيانات التجريبية، ودخول تجريبي (`admin@store.test` / `admin1234`)، وتخزين صور تجريبي. لا تحتاج Supabase ولا Cloudflare.
- **اختبار شامل** `scripts/e2e/connect.mjs`: يشغّل الثلاثة معاً في متصفح حقيقي: يفتح المتجر ويتحقق من بياناته، ثم يدخل اللوحة ويضيف علامة بصورة 12 ميغابايت (تصل 111 كيلوبايت) ويوقف حركة الشريط ويغيّر الإعلان وينشئ عرضاً ويغيّر عنوان التخفيضات، ثم يتحقق أن المتجر عرض كل ذلك.
**أخطاء وجدها الاختبار وأصلحتها:**
1. إنشاء عرض بنص إنجليزي دون عربي كان ينتهي بخطأ 500 (قاعدة البيانات تشترط العربية). الآن: رسالة واضحة بالعربية في اللوحة، والـ API يردّ 422، وأي مخالفة قيود من قاعدة البيانات تتحول إلى رد مفهوم بدل انهيار.
2. وثيقة OpenAPI كانت تصف الحقول الفارغة بشكل خاطئ (انظر أعلاه).
**ما يهمّك:** لتجربة كل شيء على جهازك: شغّل `npm run dev:local` في `store-api` ثم `npm run dev` في المتجر واللوحة مع ضبط `NEXT_PUBLIC_API_URL=http://localhost:8787` و`NEXT_PUBLIC_USE_MOCK=false`. وعلى Vercel: لا تغيّر شيئاً حتى يُنشر الـ API ويُربط بـ Supabase؛ المتجر واللوحة يبقيان على البيانات التجريبية.
**قيد معروف:** تغييرات اللوحة تظهر في المتجر خلال دقيقة إلى دقيقتين (تخزين مؤقت). سأجعلها فورية لاحقاً.

### 2026-11-26 — رفع الصور من الجهاز بصيغة خفيفة
**ما عملته:** عند اختيار صورة من جهازك (معرض الهاتف أو الكاميرا أو الحاسوب) تُصغَّر وتُحوَّل إلى صيغة **WebP** الخفيفة داخل متصفحك **قبل** الرفع.
- جرّبتها على صورة بحجم **12.2 ميغابايت: صارت 111 كيلوبايت** (عرض 600 بكسل). تظهر لك رسالة بالحجم قبل وبعد.
- المقاسات القصوى: الشعارات 600 بكسل، صور العروض واللافتات 1400، وصور المنتجات 1600 (عند بنائها). لا تُكبَّر الصورة الصغيرة أبداً، وتحتفظ الشعارات بخلفيتها الشفافة، وتُحفظ ملفات JPEG/WebP الصغيرة كما هي دون إعادة ضغط.
- **لا يستهلك الخادم أي معالجة** (التصغير على جهازك)، فالرفع سريع حتى على بيانات الهاتف، والموقع أسرع للزبائن.
- الـ API صار يتحقق من **محتوى الملف الحقيقي** لا من اسمه ونوعه المعلن، فلا يمر ملف خبيث بعد إعادة تسميته. ولم أعد أقبل **SVG** (لأنه قد يحمل سكربتاً)؛ للشعارات استعمل PNG أو WebP.
- في المتجر: أضفت `NEXT_PUBLIC_IMAGE_HOST` للسماح بعنوان صور R2، وتخزين الصور المحسّنة شهراً. والـ Next يخدم كل جهاز بالحجم المناسب له تلقائياً.
**ما يهمّك:** لا شيء الآن. عند إنشاء حاوية R2 ستضع اسم النطاق في `NEXT_PUBLIC_IMAGE_HOST` في Vercel الخاص بالمتجر.
**قيود:** صور GIF المتحركة تصبح ثابتة (أول إطار) عند الرفع من اللوحة.

### 2026-11-25 — الصور على Cloudflare R2
**ما عملته:** نفّذت قرارك بأن الصور تُخزَّن على Cloudflare R2 بدل Supabase.
- مسار رفع الصور في اللوحة (`POST /admin/uploads`) يرفع الآن إلى R2 مباشرة (توقيع آمن من الخادم)، ويعيد رابطاً عاماً من عنوان حاويتك. الأنواع المسموحة نفسها (PNG وJPEG وWebP وGIF وSVG) وبحد 3 ميغابايت.
- حذفت إعدادات Supabase Storage من قاعدة البيانات لأننا لا نحتاجها، وأضفت متغيرات R2 الخمسة إلى ملف الأمثلة (بلا قيم).
- أضفت 5 اختبارات (الإجمالي 61): تتأكد أن الطلب موقَّع كما يطلب R2، وأن الفشل لا يكشف تفاصيل، وأن الروابط والمسارات تُحوَّل صحيحاً.
**ما يهمّك:** لا تفعل شيئاً الآن. حين نصل إلى رفع الصور الحقيقية سأرشدك لإنشاء الحاوية وأخبرك بالقيم. وعند ربط المتجر سأسمح بعنوان صور R2 في إعدادات الصور.

## 4. قرارات تقنية (ولماذا)

| القرار | السبب |
|---|---|
| الـ API يتصل بقاعدة البيانات مباشرة (`DATABASE_URL`) ويستخدم Supabase للدخول فقط | يتيح اختبار كل مسار على قاعدة حقيقية دون مشروع Supabase. **هذا يضيف مفتاحين للمالك لاحقاً** (انظر القسم 5). الأمان نفسه: الاتصال من الخادم فقط. |
| **تصغير الصور وتحويلها إلى WebP في متصفح اللوحة قبل الرفع** | الخادم لا يعالج الصور (أرخص وأسرع)، والرفع خفيف على بيانات الهاتف، والمتجر أسرع. ولا نقبل SVG لأمان الموقع |
| **الصور على Cloudflare R2** (قرار المالك) بدل Supabase Storage | الرفع يتم من الـ API فقط عبر واجهة S3 المتوافقة، وتُعرض الصور من عنوان عام للحاوية (نطاقك أو `r2.dev`). أسماء الملفات عشوائية فتُخزَّن في ذاكرة المتصفح لسنة. |
| النصوص المترجمة تُخزَّن كـ `{ar, fr, en}` والعربية إلزامية | أي ترجمة ناقصة تعود للعربية تلقائياً |
| المبالغ أعداد صحيحة بالدينار، والخادم يعيد حساب المجاميع | لا نثق بأسعار قادمة من المتصفح |
| بيانات الزبون الشخصية تُحذف من قاعدتنا بعد تأكيد الطلب | شركة التوصيل تحتفظ بها أصلاً؛ نخفّف المسؤولية القانونية |
| الحركات بـ View Transitions الأصلية في المتصفح | سلسة وخفيفة، وتتراجع بلطف في المتصفحات القديمة |
| لا نضع أي مفتاح في الكود؛ كلها في متغيرات Vercel | حماية الأسرار |
